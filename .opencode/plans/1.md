# dotfiles (chrisRedwine/dotfiles) — Inventory-first macOS bootstrap with chezmoi

## Goals
1. **Minimal commands** to turn a brand-new macOS machine into “my old workstation”.
2. **Exhaustive, evidence-based**: derive repo contents from a workstation inventory, not assumptions.
3. **Secure**:
   - never commit secrets
   - inventory output is redacted + gitignored
4. **Idempotent & maintainable**:
   - re-running converges to the same state without damage
   - all machine changes implemented as repeatable scripts or declarative manifests
5. **Modern best practices**:
   - Homebrew + reproducible install approach
   - chezmoi templates + per-machine config separation

---

## Phases

### Phase 0 — Inventory (read-only, exhaustive, redacted)
**Objective:** produce an “as-is” snapshot of the current workstation: packages, tools, configs, macOS defaults, editor/terminal settings, etc., so the repo can be built from facts.

**Deliverables**
- `inventory/macos/collect.sh` (read-only):
  - runs only safe commands; no writes
  - writes machine-readable output to `inventory/output/<date>-<hostname>/`
- `inventory/macos/redact.sh` or `inventory/macos/redact.py`:
  - removes or masks likely sensitive fields (emails, hostnames, SSH hosts, tokens)
- `inventory/schema.json`:
  - describes expected output structure so we can evolve it safely
- `docs/inventory.md`:
  - what is collected, what is explicitly NOT collected, and how to review/redact

**Inventory content (macOS)**
- OS/hardware summary (versions, CPU arch)
- Shell & terminal environment:
  - iterm2 settings
  - default shell
  - zsh version
  - active frameworks and their settings
- Environment variables:
  - list of environment variables and their values
- Package managers:
  - brew taps, installed formulae/casks, leaves, `brew config`
- Applications not managed by brew (versions, paths, configuration)
- Dev toolchains:
  - git
  - ssh
  - gpg/age presence
  - language runtimes (node/python/go/rust/java)
  - version manager detection
- Editors:
  - VS Code / Cursor extensions and configuration
  - JetBrains IDEs and configuration
  - Sublime Text configuration
  - Vim configuration
- Dotfile candidates:
  - enumerate common config locations and collect **paths + checksums + sizes**
  - include contents only for an explicit allowlist
- macOS defaults:
  - collect targeted defaults domains (avoid dumping everything blindly)
  - themes
  - fonts
  - keyboard
  - trackpad
  - display
  - dock
  - screensaver
  - backgrounds
  - sound
  - network
  - dns
  - bluetooth
  - privacy
  - login items
- Background services:
  - list LaunchAgents/LaunchDaemons *names* relevant to your workflow

**Rules**
- Raw output is gitignored.
- Never collect Keychain items, private keys, browser credential stores, or token files.
- Any “content capture” must be allowlist-based.

### Phase 1 — Normalize & decide (from inventory → target state)
**Objective:** convert inventory into a “target state specification”:
- what gets managed by chezmoi (files/templates)
- what gets installed by brew (formulae/casks/taps)
- what gets applied via macOS defaults scripts
- what remains manual (or is too personal/fragile)

**Deliverables**
- `docs/decisions.md`: explicit decisions (version manager choice, terminal choice, editor scope, etc.)
- `spec/` (machine-readable target spec; keep it simple):
  - `spec/packages.yaml` (brews/casks grouped by OS)
  - `spec/macos-defaults.yaml` (settings we enforce)
  - `spec/files.md` (files we manage + rationale)

---

### Phase 2 — Implement bootstrap + chezmoi source state (macOS-first)
**Objective:** turn the target state spec into a working bootstrap.

**Chezmoi best-practice alignment**
- Use **run_once_ / run_onchange_ scripts** to apply actions safely and idempotently.
- For packages:
  - Prefer a declarative data file approach (`.chezmoidata/...`) + a `run_onchange_darwin-...` installer script pattern.
- On macOS specifically, chezmoi’s macOS guide shows embedding a Brewfile directly inside a script so it re-runs when the script changes.
- Keep local machine-specific config in `~/.config/chezmoi/chezmoi.toml` (not committed), consistent with chezmoi’s setup model (source directory vs local config file separation).
- If repo root gets cluttered, chezmoi supports using a **subdirectory** of the repo as the source state root (optional later).

**Potential repo layout (initial)**
- `README.md`
- `bootstrap/`
  - `macos.sh` — minimal entrypoint (installs prereqs; runs chezmoi init/apply)
- `inventory/`
  - `macos/collect.sh`
  - `macos/redact.(sh|py)`
  - `schema.json`
  - `output/.gitignore`
- `docs/`
  - `inventory.md`
  - `macos.md` (what is installed & configured)
  - `security.md` (threat model, secrets policy)
  - `decisions.md`
- `spec/`
  - `packages.yaml`
  - `macos-defaults.yaml`
- `home/` (chezmoi source state files live here once enabled; optional in v0)
  - dotfiles/templates/scripts (see below)
- `.github/workflows/`
  - `ci.yaml`
  - `release.yaml`
- `.opencode/` (agents + config)
  - `config.yaml`
  - `agents/`
    - `plan.md` (primary, read-only planning)
    - `inventory.md` (primary, read + restricted bash, no write/edit)
    - `security-review.md` (subagent, read-only reviewer)

**Chezmoi source content (v0)**
- Templates:
  - `dot_zshrc.tmpl`
  - `dot_gitconfig.tmpl`
  - `dot_config/...` (selected configs from inventory/spec)
- Data files:
  - `.chezmoidata/packages.yaml` (or generate from `spec/packages.yaml`)
- Scripts:
  - `run_once_darwin-prereqs.sh` (only things that should happen once)
  - `run_onchange_darwin-install-packages.sh.tmpl` (brew installs; idempotent)
  - `run_onchange_darwin-macos-defaults.sh.tmpl` (idempotent defaults)
  - (Optional) a `run_onchange_...` that embeds a Brewfile-style heredoc (aligns with macOS guide).

**Bootstrap “new machine” UX**
- Preferred:
  - install chezmoi + init/apply in minimal steps; chezmoi docs describe doing “install chezmoi and your dotfiles on a new machine with a single command” via the install script passing init args.
- Secondary:
  - brew install chezmoi → `chezmoi init --apply ...`

**Security policies**
- No “curl | bash” unless it’s a well-known upstream installer AND documented in `docs/security.md`.
- No secrets in repo. Provide hooks for 1Password but do not store secrets.

---

### Phase 3 — Validation loop (inventory → apply → inventory)
**Objective:** prove that the repo actually reproduces your workstation.
- Run inventory on current workstation
- Build repo from spec
- Apply to a clean user (or a test macOS VM)
- Re-run inventory and compare with “expected”

**Deliverables**
- `docs/validation.md`
- optional `inventory/compare.py` to diff inventory output against the spec

---

## CI requirements
- All driven by pre-commit hooks
- Shellcheck on scripts
- Linting and various file type checks (markdown, yaml, json, etc.)
- Basic chezmoi sanity checks (render templates, verify scripts are executable)
- Secret scanning (e.g., gitleaks) and block PRs if secrets detected

---

## Acceptance criteria (v0)
- Inventory scripts run safely and produce stable, redacted output.
- A brand-new macOS machine can be bootstrapped in minimal commands and becomes usable for development.
- Re-running bootstrap + `chezmoi apply` is safe and convergent (idempotent).
- No raw inventory output committed; no secrets committed.
